# Your FlowCMS site

This is a **standalone FlowCMS application**. It was generated by
`create-flowcms` and it is now yours: nothing in it points back at the FlowCMS
repository, and you can commit it, change it and deploy it as your own project.

FlowCMS is a self-hosted CMS — a public site plus an admin panel, served by
default at `/admin` and movable to any path with `FLOWCMS_ADMIN_PATH`. It is a
genuine fullstack application: route handlers under `src/app/api/` read and
write your database through Drizzle and store files in S3-compatible storage.

## What you have, and what it still needs

The application is complete. **Deployment configuration is not** — that is the
one thing scaffolding cannot decide for you.

Before the site will start you need:

| | |
|---|---|
| A database | SQLite by default. PostgreSQL, MySQL and MariaDB are supported and configured at runtime |
| Object storage | Any S3-compatible service. `docker compose up` brings up a bundled one |
| `AUTH_SECRET` | Signs every session. Whoever holds it can forge an administrator session |
| `CAPTCHA_SECRET` | Signs the login CAPTCHA challenge |

`.env.example` documents every variable inline and is the authoritative list.
Copy it and fill it in:

```bash
cp .env.example .env
```

Both secrets must be **strong random values**. The application refuses to become
ready with a weak one, and it refuses the placeholder `.env.example` ships —
that check exists because a published placeholder is a published key. Generate
them with:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
```

## Getting started

```bash
npm install                 # if you scaffolded with --skip-install
npm run build:packages      # builds the local flowcms package (see below)
npm run build
npm start
```

Or with Docker, which also brings up object storage:

```bash
cp .env.example .env        # fill in the two secrets first
docker compose up -d
```

The Docker build runs `npm ci`, so it needs a `package-lock.json` — run
`npm install` once before `docker build` or `docker compose up`.

Then open the site. It will send you to **`/setup`**, which creates the first
owner account and the site identity. That step needs `FLOWCMS_SETUP_TOKEN` set;
`.env.example` explains it. Setup closes permanently once it completes.

## Commands

| Command | What it does |
| --- | --- |
| `npm run dev` | Development server, bound to `0.0.0.0` |
| `npm run build:packages` | Build the local `flowcms` package |
| `npm run build` | Production build |
| `npm start` | Serve the production build |
| `npm run lint` | ESLint |
| `npm run typecheck` | `tsc --noEmit` — run it after a build, which generates Next's types |
| `npm run db:migrate` | Apply database migrations |
| `npm run db:bootstrap-owner` | Create the first owner without the web setup flow |

## The `packages/flowcms` directory

Your project contains a local copy of **`flowcms`**, the public FlowCMS theme
API. Themes — including the default one — import from it as `flowcms/theme`:

```ts
import { defineThemeSettings, type FlowCMSTheme } from "flowcms/theme"
```

It is a normal local dependency (`"flowcms": "file:packages/flowcms"`), which is
why `npm run build:packages` has to run before the first build. When FlowCMS is
published to npm this becomes an ordinary versioned dependency and the directory
goes away; until then, carrying it is what makes your project independent
instead of tied to a repository you do not have.

## Themes

`src/Themes/` holds all public presentation. The default theme is there and it
implements every surface. Writing your own — or installing one as a package — is
documented in `docs/themes/authoring.md`.

Installing a theme is a deliberate, reviewable edit rather than an upload: add
the dependency, add an entry in `src/Themes/packages.ts`, add a Tailwind
`@source` line in `src/app/globals.css`, and rebuild. Switching between themes
you already have is a runtime setting in **Appearance**, with no rebuild.
